# Browser Companion Architecture

The browser companion is an optional local bridge for browser extensions that can provide richer metadata than a desktop window title. It is disabled by default.

## Threat model and boundaries

- The desktop service binds only to `127.0.0.1`; it never listens on LAN/public interfaces.
- The extension must authenticate with a random per-user bearer token.
- The token is generated by the desktop application and stored under the user's configuration directory with restrictive permissions where supported.
- Requests with an extension `Origin` are accepted only from `chrome-extension://` or `moz-extension://` origins.
- Request bodies are capped at 16 KiB.
- Companion state expires after a short TTL and is kept in memory only.
- Private/incognito activity always discards title, service, and URL regardless of what the extension sends.
- URL fragments are always removed.
- Exact URL path/query collection is disabled by default and requires explicit user opt-in.
- With the default policy, the desktop receives at most the URL origin (`scheme://host`).
- No companion data is uploaded by this component. Discord only receives the final Rich Presence payload after the normal privacy redactor runs.

## Local endpoint

When enabled, the default endpoint is:

`POST http://127.0.0.1:17653/v1/activity`

Authentication header:

`Authorization: Bearer <per-user-token>`

The token is stored in:

- Linux: next to `~/.config/discord-rich-presence/config.yaml`, under `companion/token`.
- Windows: next to `%APPDATA%\discord-rich-presence\config.yaml`, under `companion\token`.

A simple health endpoint is available at `GET /health` and contains no browser data.

## Payload

The extension may send a JSON object containing:

```json
{
  "browser": "Firefox",
  "service": "YouTube",
  "title": "Example video",
  "url": "https://www.youtube.com/watch?v=example",
  "private": false
}
```

All fields are optional. The desktop applies its own policy before accepting them.

## Recommended extension permissions

A future extension should request the smallest possible permission set. Prefer active-tab/tab-change events over broad history access. Do not request browsing history, cookies, passwords, form data, downloads, or network interception merely to populate Rich Presence.

The extension should:

1. Send data only for the active tab/window when the browser provides a documented API.
2. Send `private: true` without sensitive fields for private/incognito contexts.
3. Avoid storing the desktop token in sync/cloud storage.
4. Never send browser data to a remote service.
5. Treat the desktop response as an acknowledgement only; no browser data is returned.

## Desktop policy settings

`browser_companion.enabled`: starts the loopback listener.

`browser_companion.allow_titles`: allows page titles.

`browser_companion.allow_origin`: allows `scheme://host` when exact URLs are disabled.

`browser_companion.allow_exact_url`: explicit opt-in for URL path/query. Fragments are still removed.

`browser_companion.ttl_secs`: expires stale extension activity.

Strict privacy mode still removes browser URLs/buttons from the final Discord payload.

## Failure behavior

If the companion is unavailable, unauthenticated, stale, malformed, or disabled, normal window-title browser detection continues. The service never guesses an exact URL from browser processes or unrelated background state.
